P14 · 60 minutos · Dossiê e diagnóstico técnico

O caminho completo de uma requisição web

Relembre o percurso que uma requisição percorre dentro do sistema operacional:

  1. Rede e E/S: o kernel recebe os dados da interface e os disponibiliza ao processo. As práticas desta trilha não abriram sockets nem capturaram tráfego; esta etapa é uma explicação conceitual.
  2. Chamadas de sistema: o processo solicita leitura e escrita ao kernel. ENOENT informa arquivo ausente; a aplicação escolhe construir uma resposta HTTP 404.
  3. Escalonamento: tarefas prontas disputam CPU. FCFS, SJF e RR foram modelos didáticos; a simulação não identifica a política efetiva do Linux.
  4. Isolamento e concorrência: processos têm espaços virtuais separados; threads do mesmo processo compartilham dados e precisam coordenar atualizações. Mutex protege a região crítica, não todo acesso ao servidor automaticamente.
  5. Memória e arquivos: ausência no cache da aplicação não implica necessariamente page fault. Leituras de arquivos podem usar o page cache do kernel; acessos à memória virtual podem gerar faltas, inclusive sem leitura do disco.
  6. Permissões: o kernel verifica o acesso segundo identidade e permissões dos arquivos e diretórios. Modo 644 não publica um arquivo na web por si só: o serviço precisa ter acesso e configurá-lo para atendimento.
  7. Resposta e logs: um servidor real envia a resposta ao cliente e registra o atendimento. Nesta trilha, respostas e logs foram arquivos locais; stdio e page cache podem adiar transferências. Encerrar a escrita não demonstra persistência no dispositivo.

Mudança orientada e evidências

Compare dois projetos: um processo por cliente e threads no mesmo processo. Use ao menos três evidências das práticas, identifique dados compartilhados e proponha uma proteção. Diante de um arquivo ausente, explique separadamente errno, decisão HTTP e registro de log.

O joystick e a gravação do savegame

Compreenda como o console se comunica com o mundo exterior: a leitura dos botões do controle por interrupção e o ganho de velocidade ao salvar o jogo com buffers.

Duração: 60 min Entrada/Saída, barramentos, polling, interrupções e buffers

Prof. Me. Juvenal Silva Neto · Ciência da Computação

Respostas salvas automaticamente neste navegador.

O cenário do jogo

Periféricos, barramentos e persistência de dados

Um videogame não funciona apenas dentro da CPU e da RAM: ele precisa receber comandos do jogador através do joystick (dispositivo de entrada) e gravar o progresso da fase no cartão de memória ou disco (dispositivo de saída e armazenamento). A comunicação através dos barramentos de E/S é milhares de vezes mais lenta do que a CPU interna. Por isso, sistemas bem projetados utilizam interrupções de hardware e buffers de transferência em bloco para não travar a jogabilidade.

02 Gravando dados

Crie e execute a rotina de savegame

Crie o arquivo io_game.c, compile e execute para comparar a gravação byte a byte versus a gravação em bloco com buffer:

Criar io_game.c
cat > io_game.c <<'FIM'
#include <stdio.h>

int main(void) {
    // Dados da partida salvos pelo jogo:
    unsigned char save_original[4] = {
        3,   // Byte 0: Vidas restantes
        2,   // Byte 1: Numero da fase
        50,  // Byte 2: Pontos ganhos
        99   // Byte 3: Segundos restantes
    };

    printf("=== SALVANDO DADOS DO JOGO NO ARMAZENAMENTO ===\n");

    // Metodo 1: Gravacao de 1 byte por vez (multiplos acessos lentos ao barramento)
    FILE *f1 = fopen("save_byte.dat", "wb");
    if (!f1) { perror("save_byte.dat"); return 1; }
    for (int i = 0; i < 4; i++) {
        fwrite(&save_original[i], 1, 1, f1); // 4 chamadas de E/S
    }
    fclose(f1);

    // Metodo 2: Gravacao em lote com buffer/DMA (1 unico acesso em bloco)
    FILE *f2 = fopen("save_bloco.dat", "wb");
    if (!f2) { perror("save_bloco.dat"); return 1; }
    fwrite(save_original, 1, 4, f2); // 1 chamada de E/S
    fclose(f2);

    puts("Arquivo 'save_byte.dat' gerado com 4 transferencias de 1 byte.");
    puts("Arquivo 'save_bloco.dat' gerado com 1 transferencia em bloco de 4 bytes.");

    // Modelo comparativo de entrada do controle:
    puts("\n=== MODELO DE LEITURA DO JOYSTICK / CONTROLE ===");
    puts("1. POLLING: A CPU pergunta em loop 'Apertou botao?' -> Desperdiça tempo da CPU.");
    puts("2. INTERRUPCAO: O controle avisa a CPU somente quando o botao eh pressionado -> CPU fica livre.");

    return 0;
}
FIM
gcc -std=c11 -Wall -Wextra -O0 io_game.c -o io_game
./io_game
Saída esperada

Arquivo 'save_byte.dat' gerado com 4 transferencias de 1 byte.

04 Polling vs Interrupção

Como o console deve escutar o controle?

Imagine que o jogo rode a 60 quadros por segundo. Se usarmos Polling, a CPU precisará parar sua execução dezenas de vezes a cada quadro apenas para perguntar ao controle: "O botão de pulo foi pressionado?". Na maioria das vezes a resposta será "Não", desperdiçando tempo precioso que poderia ser usado para calcular a física e os gráficos do jogo.

Com Interrupções de Hardware, o processador trabalha focado exclusivamente no jogo. Quando o jogador aperta o botão no joystick, o hardware do controle gera um sinal elétrico de interrupção na placa-mãe. A CPU pausa momentaneamente o que estava fazendo, atende o pulo e retoma o jogo em frações de microssegundo.
